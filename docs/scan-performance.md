# 扫描性能

交互式工作树 / 依赖页先发现目录，再在后台完成空间、引用、运行状态和活跃度检查。首次发现目录前显示 loading 动画和耗时，隐藏空表格与零计数；发现结果后才切换到列表。列表提前可见不代表测量已完成；完整检查结束前不开放清理。JSON、文本、MCP 和指定路径操作仍等待完整结果。

## 真实目录的盘点与复核（本地修复）

完整依赖报告的时间主要花在目录遍历和 Git 子进程上，本次只减少重复工作，不改变清理结论：

- 只找目录和链接的遍历（数据目录、Git 登记的关联工作树）直接使用目录项自带的类型，不再为每个文件单独查询元数据；文件系统不提供类型时才回退到逐项查询。目录仍以不跟随链接的方式打开，打开后再确认确实是目录。
- 列目录不再为同一目录重复打开一次。
- 同一份报告内，所属仓库按目录缓存；每个仓库只读取一次跟踪文件清单，并用一次批量查询判断哪些产物被忽略。文件名含通配字符、非 ASCII 字符，或批量结果不完整时，回退到原来的逐项 Git 查询。结果不跨报告复用，暂存前的逐项复核照常重新查询。
- 关联工作树位于另一个已完整遍历的工作树内部、且中间不经过被跳过的目录时，不再重复遍历。
- 等待子进程改为阻塞在输出管道上，不再每 2 毫秒轮询；超时和取消照常生效，取消最迟约 20 毫秒被发现。

`deps --timings` 在标准错误输出各阶段的累计耗时和次数，报告内容不变。子进程行同时计入发起它的阶段，各行相加会超过合计。

2026-11-11，macOS Apple Silicon，实际主目录：2,094 个条目（1,683 个产物目录、411 个链接）、25 个项目。只读运行 `deps --json`，修复前后各一轮，先后执行；Agent 运行期间磁盘缓存和目录内容都会变化，单轮结果只说明量级。

## 批量暂存复核（本地修复）

旧实现对每个选中产物分别生成完整报告，移动前又生成一次；每份报告都重新统计所有工作目录的大小。选择 N 项时，会执行约 2N 轮全范围引用复核和工作目录大小统计。

现在同一 Agent 的选中产物共用一次批量预检查，只测量选中产物，不再计算用于展示的工作目录总大小。移动前，同批次的引用复核结果在 30 秒内复用，超过时限才重新核对（`vault::STAGE_REVIEW`）；临时清除复用 10 秒（`vault::PURGE_REVIEW`）。无论是否复用，每项移动前仍单独比较目录身份、变更标记和内容摘要，复核未核实或发现新增引用时继续保留目标，不复用页面上已经过时的清理结论。

引用复核需要覆盖 Git 登记的关联工作树，包括列表范围以外的主仓库。大仓库和大量选中项仍需要等待；界面会区分扫描与执行操作，显示暂存项序号、已完成工作树数量、已遍历条目数和总耗时。

使用真实终端交错测试两个构建的批量暂存耗时，只在临时 HOME 中创建样本并验证暂存和恢复：

```sh
.venv/bin/python dev/rust-stage-benchmark.py \
  --before /绝对路径/修复前程序 \
  --after target/release/clean-my-agent
```

2026-11-11，macOS Apple Silicon，8 个选中产物、另有 20,000 个未选中产物文件，预热后交错执行 3 轮。同一脚本、同一机器，对比本轮起点构建（只含首轮批量预检查）与当前构建：

| 构建 | 中位耗时 | 三轮耗时（秒） |
| --- | ---: | --- |
| 只含批量预检查 | 0.618 秒 | 0.6180 / 0.6199 / 0.6172 |
| 当前（共用复核结果） | 0.1585 秒 | 0.1580 / 0.2105 / 0.1585 |

再以更早的原代码构建运行同一脚本，中位耗时为 1.3327 秒（1.3343 / 1.3327 / 1.3317），与当前构建相比约 -88%。每轮验证了暂存和恢复；测试采用暖缓存及相同的隔离进程检查结果，不包含首次报告扫描，也不能直接推算真实大工作树的耗时。第三轮 0.2105 秒是偶发波动，中位数不受影响。

真实大目录的指定路径复核（`deps <路径> --json`，25 个关联工作树，单路径）在同一台机器上交错执行：修复前 243.3 秒，复用复核结果后 147.8–159.0 秒，减少约 35–39%。剩余时间几乎全部是工作树完整占用统计，未随本次修改变化。

## 操作后的局部刷新（本地修复）

暂存、恢复、永久清除和整树删除成功后，当前列表不再整页重扫：按操作返回的路径移除已移动项，重新计数所属项目的产物，并从已测量大小中减去移出部分，提示「已按操作结果更新列表；其余内容沿用上次核查，r 可完整刷新」。未移动的行保留上一次核查结论，不会因刷新而变成未测量。

以下情况仍完整重扫：结果不确定或失败、结果没有给出路径、会话操作（改变状态而非路径），以及返回总览（总览总数由各页汇总，需要重新统计）。取消确认不触发任何重扫。

## 折叠目录占用（本地修复）

完整文件盘点会把多数顶层目录折叠成一个数，原先生成一次系统 `du -k -s -x` 子进程。现在在同一进程内按相同口径遍历：

- 只累加分配块，按 KiB 向上取整；
- 跨目录的硬链接只计一次，由先到达的目录计入；
- 不跨挂载卷，不跟随链接；
- 目录项由一次批量读取取得元数据（macOS），批量结果不完整时逐项回退；无法批量读取的平台逐项查询；
- 进度、取消和逐目录错误提示与其它阶段一致，无法完整读取的目录报告为部分占用。

单元测试用同一组目录（跨目录硬链接、稀疏文件、符号链接、空目录）与原生 `du -k -s -x` 的输出逐路径比较，结果相同。该机器上 43 个折叠目录仅 `du` 子进程本身就需要约 72 秒墙钟（用户态 0.9 / 内核态 32.8 秒，46% CPU），大部分时间在等待 I/O。

第一版进程内实现沿用逐项元数据查询，交错实测完整 `scan --json --agent all` 为 209.7–222.9 秒，而仍调用 `du` 的构建为 160.0–174.1 秒——每个文件多一次系统调用，反而慢了约 25%。折叠目录改用批量读取后，两轮交错测试为 159.4–166.3 秒，对照 160.0–162.3 秒，与 `du` 持平；折叠目录合计只有运行期间自然增长（几十 KB 到约 1 MB）量级的差异。因此收益是不再依赖外部命令，并与其他阶段共享取消和错误处理，墙钟没有缩短。

Linux 与非 macOS 平台的 `listing()` 仍逐项查询，因此那里的折叠目录统计与本机 `du` 之间的耗时关系未在本机测量。

## 批量元数据与受控并发（本地 P2 试验）

以下是先做微基准、再按结果决定是否采用的项：

| 试验 | 结果 | 结论 |
| --- | --- | --- |
| macOS `getattrlistbulk` 批量读取目录项 | 同一棵大目录树（需完整元数据）逐项 `fstatat` 约 13.0 秒，批量读取约 5.4–5.8 秒 | 已用于数据目录的详细遍历（项目占用与活跃度）和折叠目录统计；产物测量需要逐文件属性和硬链接去重，仍逐项查询 |
| 多线程分摊独立目录树 | 4 棵树、完整元数据：1 线程约 48.5 秒，2 线程约 24.5 秒，4 线程约 12.5–13.7 秒 | 产物测量按目录分发到工作线程；默认 macOS 4 线程，其它平台 1；`CLEAN_MY_AGENT_SCAN_WORKERS` 可覆盖 |
| Linux `statx` | 本机为 macOS，无法测量 | 未实现；Linux 代码路径保持 `fstatat` |
| 用类型化结构替代 `serde_json::Value` | 完整报告用户态约 12 秒、内核态约 107 秒 | 未采用；收益上限是总耗时的十分之一量级，而改动面覆盖全部报告结构 |
| 按目录标记落盘缓存展示结果 | — | 未采用；缓存一旦参与判断就可能把过期结论带入清理，若只做展示又不能省下真正耗时的测量 |

以上微基准使用独立的 C 程序在同一批真实大目录上交替执行，只记录计数和耗时，不读取文件内容；机器同时运行其它 Agent 进程，绝对值有波动，只用于比较同一组内的相对关系。

## Rust 0.4.0

当前运行时使用 Rust 原生目录遍历、系统文件元数据和受控子进程；完整文件盘点的折叠目录由进程内统计代替系统 `du`。引用检查不再依赖 Python 调用 `find`。界面先绘制 loading，再启动后台扫描；发现工作目录后可先显示预览，完整检查结束前禁用清理。子页面进入和手动刷新会重新扫描；只读浏览后返回总览复用本次完整结果，执行操作后失效。

复用产物测量结果统计项目占用，避免重复深度遍历，并保留硬链接去重、共享块计算和执行前复核。缓存标记不存在时先做廉价的元数据检查；标记存在时继续完整的路径与身份校验，减少在普通目录上重复检查祖先路径。界面只保持一个后台扫描任务；`CLEAN_MY_AGENT_SCAN_WORKERS`（1–8）在 Rust 版生效，控制只读扫描的工作线程数：macOS 默认 4，其它平台默认 1。

2026-11-10，macOS Apple Silicon，4 个临时 Git 项目、80,000 个文件，包含跨源码 / 产物硬链接和外部符号链接。每个实现预热一次，再交错执行 3 轮；Rust 使用 release 优化构建，Python 使用迁移开始时的源码快照。计时包含程序启动、Git 检查、遍历和 JSON 输出；进程检查使用双方相同的隔离固定结果。

| Rust 0.4.0 | 0.8480 秒 | 1.1581 / 0.8480 / 0.8440 |

忽略采集时间后报告一致，双方无扫描错误。最终构建复测中，该样本耗时减少约 **21%**；首轮测得约 28%，复测存在运行波动。这是暖缓存、受控进程检查的结果，不代表真实主目录或冷磁盘上的固定倍数。

## Python 0.3.2 历史优化

以下记录仅描述迁移前的 Python 实现，保留用于对照。缓存、`find` 批处理和并发环境变量不描述当前 Rust 实现。

- 同一次报告中，深度测量产物时同时收集占用摘要，统计工作树时跳过这些已测子树。保留跨产物、源码和目录内部的硬链接去重；稀疏文件按实际分配块计算，链接不跟随。
- 交互模式的引用检查也使用每批最多 64 个工作树的 `find`，保留 NUL 分隔的文件名和实际完成数量。
- 多 Agent 报告共用一次会话活动索引读取；测量结束后的引用复核和运行状态检查继续执行。
- 首页与子页面之间复用本次运行的完整报告，显示采集时间，手动刷新或执行操作后失效。缓存不写磁盘，不根据顶层目录修改时间推断所有后代都未变化。
- 清理执行前重新盘点，最终移动前继续执行原有策略、引用、安装证据和进程检查。历史快照保持只读。

macOS / Linux 支持 1–4 路受控并发，进度回调集中回到调用线程。默认 1 路：本机实测多路扫描的完整耗时更长，因此没有默认开启。较慢的存储可自行比较：

```sh
CLEAN_MY_AGENT_SCAN_WORKERS=2 clean-my-agent deps
```

省略该变量即恢复默认；不需要安装新的扫描工具。Windows 继续使用现有只读扫描后端，交互页面同样先列目录。
